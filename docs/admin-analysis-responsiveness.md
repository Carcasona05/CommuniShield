# Analysis and status responsiveness

## Behavior

- Hotspots, risk outlook and sentiment analytics have administrator/filter-scoped, bounded server snapshots. Concurrent identical reads share one build; revisiting within 60 seconds does not recompute. From 60 seconds to five minutes the last successful result returns immediately while a tracked background refresh runs. Older snapshots require a successful rebuild. Failed builds never become empty/zero success responses.
- Every request still verifies administrator access. Snapshots include their actual update time and refresh/error state. The frontend retains maps/charts during refresh; Sentiment Analysis now uses the same validated retained query as Hotspots/Risk, with inline retry instead of silently showing empty defaults.
- Successful relevant writes and AI job completion invalidate process snapshots. A generation fence prevents pre-write calculations from repopulating the cache. Independent analytics relations load concurrently. Server-Timing headers distinguish status-save, hotspots, risk and sentiment request durations.
- Status, review-score triggers, audit and background outbox now commit in **one database transaction**. The response waits for that commit, not notifications or Gemini. It returns effective status/verification values. Failed commits return errors without a false save confirmation. Unchanged status/verification does not create more jobs.
- Re-analyze queues up to 50 report IDs per request. PostgreSQL discovers **all existing comments**, including previously successful ones. Each credibility/report sentiment/comment sentiment call is a separate durable task. Active work is deduplicated across concurrent requests and server instances.
- The UI reports queued/running/completed/failed/partial progress, including per-post task counts, without blocking navigation or closing access to other controls. Polling is focus-aware (five seconds). Active batches recover after refresh. Completion refreshes affected read models and the currently inspected document, not a full-page reload. Enqueueing alone does not invalidate displayed analysis.
- Workers use SKIP LOCKED claims, renewable leases, token-fenced completion, up to three attempts with backoff, and explicit terminal failure/skipped states. A disappeared/deleted subject is skipped, not called successful. Completed/failed/skipped AI tasks are audited. Notification delivery is at-least-once: a worker crash during fan-out can repeat a notification; delivery is not claimed to be exactly-once.

## Deployment (required)

1. Apply `DB_Schema/migrations/admin_analysis_jobs.sql` to Supabase **before deploying this backend**. It is additive/idempotent, creates service-role-only tables/functions with RLS enabled, and preserves existing report scoring triggers. Without it, status saves and queue requests explicitly fail rather than silently reverting to slow/lossy behavior.
2. Deploy/restart the backend, then rebuild/deploy the frontend. Legacy synchronous AI endpoints remain compatible; the Report Management UI uses the new queue.
3. Long-running Node/Render starts a dedicated two-worker analysis loop every five seconds, separate from comment-insertion recovery. Each process permits at most two admin workers.
4. **Serverless deployments need a scheduler** calling `GET /api/jobs/admin-analysis` with `Authorization: Bearer <CRON_SECRET>`. Schedule at the cadence allowed by the host (e.g. every minute); allow sufficient function duration for one provider call. Queue requests and visible progress polls also wake a worker, but are not a replacement for unattended recovery. No hosting-plan-specific cron schedule is silently installed. Multiple scheduler invocations/instances can safely claim distinct jobs. Per-process concurrency is not a global provider rate limit.
5. Verify status changes, owner/nearby/admin notifications, archive silence, audits, queue recovery after restarting a worker, failure/retry states, and both roles' retained charts/maps. No live migration, scheduler setup or production deployment is performed by these code changes.

## Distribution-only date filter

Sentiment Distribution owns its own Today (default), Past 7 Days (today plus six preceding calendar days), Past 30 Days (today plus 29 preceding calendar days), and All Time filter. Its dedicated `/admin/sentiment-distribution?period=today|7d|30d|all` endpoint uses Philippine calendar boundaries. Reports and comments are filtered by their **own** creation timestamps, so a new comment on an old non-archived report counts today. Archived reports and their comments are excluded; future-dated subjects are excluded. Analysis timestamps do not decide the selected period.

The distribution bars and its Analysis coverage counts change together. Overview, training/model panels, Hotspots and Risk are not filtered or refetched by this control. Loading/retry is confined to the card, and previous-period rows are never relabeled as the new selection. Filter/day-specific session caches also partition at Philippine midnight.

The endpoints read compact IDs/creation dates/status/labels only, follow exact-count database pages even when the host returns fewer than 500 rows, and bound sentiment ID-query sizes/concurrency. All Time does not inherit the legacy analytics endpoint's 30-day cutoff or a 1,000-row response cap. Reads explicitly fail above 100,000 subjects of either type rather than presenting truncated counts. No new SQL migration is needed for these filters; deploy the new backend endpoints before the frontend.

## Independently filtered overview and real sentiment trend

`/admin/sentiment-overview` and `SentimentOverviewCard` own a separate Today (default), Past 7 Days, Past 30 Days, All Time selection. The overview's totals and graph use the same selected subjects and Philippine boundaries, but changing this filter never changes the distribution selection or remounts training. Both endpoints share a scoped server aggregation for identical periods to avoid duplicate database work.

The overview's compact banner and header use the same trend buckets as the graph. **AI Analyzed** counts only positive/neutral/negative results; **Reports & Comments** adds records without successful results to that classified count. Unclear results and aggregate tie labels are excluded from both numbers, not reclassified as unsuccessful. **No Successful Result** still counts pending, failed, unavailable or missing analyses. Unclear remains visible in the separate Analysis Coverage section, whose raw counts are unchanged. **Positive Sentiment** is `positive / (positive + neutral + negative) * 100`; with no classified results it is unavailable, not zero. The inverted/unvalidated `Avg. Health` rating and Anxious/Calm graph labels are removed from this page; legacy analytics consumers remain compatible.

The graph retains the original smooth blue line style, with Negative at the top, Neutral / balanced in the middle, and Positive at the bottom (not unmeasured anxiety/calm emotion labels). Its explicitly defined balance is `(negative - positive) / (positive + neutral + negative)`, where neutral results dilute but do not tilt the line. Mixed is an aggregate tie label, not a fourth classification: it is excluded from the graph's counts, percentages and balance. Equal positive and negative results can also be centered; this is not a health or safety score. Bounded cubic curves never join across missing-data gaps. Today has Philippine hourly bins; seven/thirty-day views have daily bins. All Time groups the entire available history into at most twelve monthly or multi-month bins, without dropping older records. Hover, keyboard focus or tapping an interval shows a compact in-plot tooltip with only Negative, Neutral and Positive counts. The tooltip hides on mouse leave and is clamped within the plot. Gaps remain gaps; future hours are marked upcoming. The graph scales to its container with fewer axis labels on narrow screens and no horizontal scrolling. Graph updates and tooltip entry animate subtly; reduced-motion preferences disable those animations. Neither overview nor distribution loading replaces the whole page.

## Limits and verification

- The server snapshot cache is process-local (100 entries), not a persistent shared cache. Cold starts still pay the real database/computation cost. Other instances and out-of-band database writes become visible on TTL refresh; this is not a globally instantaneous invalidation mechanism. Browser/session snapshots retain the existing account/backend isolation rules.
- Manual jobs snapshot the report's comments at enqueue time. Comments arriving later follow the existing comment-sentiment insertion queue. Inputs are read authoritatively when each task executes. Batches with more than 50,000 comments explicitly ask for a smaller selection.
- Jobs and audit history are retained; introduce an operational archival policy before very large deployments. No potentially user-owned history is automatically deleted.
- Run `npm run test:admin-fetch` in `server/` and `clients/`. Run `tests/database/adminAnalysisJobs.postgres.mjs` with PGlite (`PGLITE_MODULE` may point to an external install) for real PostgreSQL transaction/deduplication/lease/permission checks. The browser fixture in `server/tests/adminFetching.browser.mjs` checks queued re-analysis without synchronous AI calls and navigation during background work.
- Compare Server-Timing, transfer sizes, queue timestamps and provider durations on the same production dataset/device/network. No unmeasured production speedup percentage is claimed. The queue improves responsiveness and recovery; it does not make external AI inference instantaneous.
